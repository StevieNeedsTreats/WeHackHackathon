Three optimizations to the TruthGraph graph

These changes are live in the code. Switch each diagram between Before and After to see what changed. The examples are made up to show the idea, but the changes are real.

Optimization 1 Better reuse

Findings now connect to the hypothesis they're about

Before, two different agents named the same idea. The Intake agent called the outcome "muscle mass". The Extractor read each paper and used the paper's wording, such as "lean body mass" or "fat-free mass".

Each name became its own Concept node. So a finding about "lean body mass" never linked to the hypothesis about "muscle mass", even though they mean the same thing.

What changed: while the Stance agent judges each finding, it now also says whether the finding measures the hypothesis's outcome. If it does, the finding is linked to that Concept and its wording is saved as a synonym. When a new question uses a synonym, the Intake step resolves it to the existing Concept, so earlier research is reused.

Findings about muscle mass: 1 of 3
Before: asking the graph "what do we know about muscle mass?" found only paper A. Papers B and C hung off separate Concept nodes that no hypothesis pointed to.
Optimization 2 18× fewer rows

The canvas now fetches each paper once

When the canvas loads, one query fetches each paper together with its authors, funders and labs. Before, it asked for all three in one go, so FalkorDB returned every combination of them, one row each.

A paper with 3 authors, 3 funders and 2 labs came back as 3 × 3 × 2 = 18 rows, and the code threw 17 of them away.

What changed: the query now asks for each list separately, using pattern comprehensions. Each paper comes back as one row with three short lists, and the canvas gets exactly the same data. In a benchmark the query time stayed about the same (around 40 ms), because sending the papers themselves takes most of that time.

The app keeps at most 3 authors, 3 funders and 2 labs per paper, so 18 is the most one paper can produce. The count also repeats for every hypothesis that considered the paper. The code is in snapshot() in backend/app/graph.py.
Optimization 3 Shorter queries

Findings now jump straight to their paper

Many queries start at a Finding and need its Paper, for example to show the title or find the funder. Before, they had to step through the Study in between, every time.

What changed: each finding now stores its paper's id when it's extracted, and older findings get it filled in when the app starts. Queries that only need the paper jump straight to it. Study stays in the graph for the screens that show study details.

The funding trail query went from 5 hops to 3, and "who contradicts whom" from 7 to 4.

Finding to Paper: 2 hops
The Cypher pattern before:
(f:Finding)<-[:FOUND]-(:Study)<-[:DESCRIBES]-(p:Paper)
